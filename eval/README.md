# Оценка качества

Отбор вакансий и дедупликация работают на правилах, поэтому качество проверяется
на ручной разметке, а не по ощущениям от сводки. Правила разметки и решения
по пограничным случаям — в [`LABELING.md`](LABELING.md).

## Методология

- **dev / test.** Правила дорабатываются по ошибкам на dev-разметке, поэтому
  метрики на ней оптимистичны. Версия после доработки фиксируется тегом git,
  а итоговые метрики считаются на test — следующей неделе, размеченной без взгляда
  на предсказания и закоммиченной до первого прогона. После разбора ошибок
  test-неделя становится dev для следующей итерации.
- **Test-неделя.** Вакансии, впервые увиденные ботом за неделю после заморозки
  правил. Из нее убраны вакансии dev-недели (по url и по паре компания + название)
  и перепосты внутри недели: роль определяется по названию, повтор был бы тем же
  примером и сделал бы интервалы ложно узкими.
- **Качество разметки.** В лист test вслепую подмешаны 50 вакансий из dev
  (поровну DS и не-DS), по ним считается согласие с собой.
- **Интервалы.** 95% bootstrap, 1000 ресемплов; версии правил сравниваются
  на одних и тех же ресемплах.
- **Версии.** `--rev` подставляет словари правил из любой ревизии git, так что
  любую версию можно оценить на любой разметке.
- **Данные.** Снапшоты вакансий лежат в `data/eval/` и в git не попадают,
  разметка связана с ними по `url`.

## Отбор DS-ролей — `evaluate.py`

### Test: `gold_v2.csv`

1739 вакансий, впервые увиденных ботом за неделю в середине октября 2026,
из них 139 с DS-ролью. Правила заморожены на `taxonomy-dev-v1`.

| Версия | Precision [95% ДИ] | Recall [95% ДИ] | F1 [95% ДИ] |
|---|---|---|---|
| наивный baseline (data / ml / ai в названии) | 0.55 [0.48, 0.62] | 0.83 [0.76, 0.89] | 0.66 [0.60, 0.71] |
| `taxonomy-dev-v1` | 0.98 [0.94, 1.00] | 0.64 [0.56, 0.72] | 0.77 [0.71, 0.83] |

Precision переносится с dev (1.00) на новую неделю, recall — нет (0.90 → 0.64):
правила выучили словарь dev-недели. Попадание в сводку (DS-роль и сфера из списка):
P 0.91 [0.83, 0.97], R 0.49 [0.40, 0.57]. Сферы у DS-вакансий: micro F1 0.58
[0.50, 0.65], лучше всего fintech — F1 0.80 на 43 вакансиях.

Согласие разметки с собой (50 вакансий из dev, размеченных вслепую второй раз):

| Что сравнивается | Совпало                |
|---|------------------------|
| DS-роль | 50 из 50, kappa = 1.00 |
| роли у DS-вакансий | 20 из 25               |
| сферы у DS-вакансий | 24 из 25               |

Роли — самая неоднозначная часть разметки, это потолок для метрик по сферам.

Что нашел разбор ошибок. Пропущено 50 DS-вакансий:

- 21 — словарь хранилищ и платформ данных: DWH, КХД, ETL, Greenplum,
  «разработчик хранилища данных», Chief Data Officer. Алиасы data engineer
  покрывают только само название профессии;
- 16 — руководящие роли: «тимлид DS», «Data Science Team Lead», «Head of Analytics»,
  «Team Lead Data & AI». Из руководящих в словаре только head of ml / head of ai;
- 9 — ML внутри названия обычной роли: «Python-разработчик (ML/LLM)»,
  «ML-аналитик / аналитик качества ИИ-помощника»; «MLOps/DevOps» срезало
  исключение devops;
- 4 — кванты: решение «quant researcher — DS-роль» принято при разметке
  test-недели, в правилах его еще нет.

2 ложных срабатывания — продакт-менеджеры AI/ML-продуктов: алиас `ai/ml`
ловит название продукта, а не роль.

Сферы:

- все 9 срабатываний healthtech ложные: «медицин» и «клиник» находятся
  в блоке условий — ДМС, компенсация медицинских расходов;
- it найдена у 13 из 43 вакансий: IT-компании, интеграторы и аутсорс
  (IBS, Usetech, Джетлин) не распознаются по ключевым словам. Что считать
  сферой интегратора — и самое спорное правило разметки.

### Dev: `gold_v1.csv`

374 вакансии за неделю в конце сентября 2026, из них 80 с DS-ролью.

| Версия | Precision | Recall [95% ДИ] | F1 |
|---|---|---|---|
| наивный baseline (data / ml / ai в названии) | 0.80 | 0.71 [0.62, 0.81] | 0.75 |
| до разбора ошибок (`528b8b8`) | 0.98 | 0.75 [0.65, 0.84] | 0.85 |
| `taxonomy-dev-v1` | 1.00 | 0.90 [0.83, 0.96] | 0.95 |

Что нашел разбор ошибок:

- около 14% DS-вакансий не попадали ни в одну сферу — так появилась сфера IT / Bigtech;
- продукты экосистем уходили в сферу материнской компании (GigaChat по слову
  «сбер» → fintech) — добавлены исключения для подразделений;
- не хватало алиасов для RL / LLM / applied scientist и руководящих ролей.

## Дедупликация — `evaluate_dedupe.py`

`dedupe_gold_v1.csv`: 232 пары вакансий одной компании за неделю в начале октября
2026 — 72 дубля, 159 разных вакансий, 1 спорная. Метрики считаются по парам,
отдельно для пар с разных бордов и с одного. Test-разметки для дедупликации
пока нет, это метрики dev.

| Версия | Precision | Recall [95% ДИ] | F1 |
|---|---|---|---|
| наивный baseline (одинаковые названия) | 0.90 | 0.38 [0.27, 0.49] | 0.53 |
| похожесть названий (`a91cc6f`) | 0.72 | 0.61 [0.50, 0.72] | 0.66 |
| + общий текст описаний (`dedupe-by-description`) | 0.79 | 0.51 [0.39, 0.64] | 0.62 |
| `dedupe-dev-v1` | 0.98 | 0.90 [0.83, 0.97] | 0.94 |

Что нашел разбор ошибок:

- hirify дописывает к названию отрасль в скобках и пересказывает описание:
  у настоящих дублей общего текста почти нет, и порог по тексту разрывал их;
- на одном борде одинаковое название часто означает разные вакансии
  (разные команды, города) — там нужен общий текст;
- одна компания записана разными алфавитами: «Яндекс» / «Yandex»,
  латинская «A» в «Альфа».

Recall считается среди пар-кандидатов: похожие названия или общий текст.

## Что дальше

- test-неделя v2 становится dev: правила дорабатываются по ее ошибкам (`taxonomy-dev-v2`);
- рядом с правилами — классификатор по названиям, обученный на v1 + v2,
  и LLM zero-shot baseline;
- все варианты сравниваются на v3 (v2 для дедупликации) — следующей неделе,
размеченной по той же процедуре.

## Запуск

```
# разметка: выгрузка недели с копии серверной базы и импорт после разметки
python -m eval.labeling export --gold v3 --since YYYY-MM-DD --until YYYY-MM-DD
python -m eval.labeling import --gold v3

# отбор DS-ролей
python -m eval.evaluate --gold v2 --rev taxonomy-dev-v1   # test, замороженная версия
python -m eval.evaluate --rev taxonomy-dev-v1             # dev
python -m eval.evaluate --gold v2                         # рабочая копия

# дедупликация
python -m eval.evaluate_dedupe --rev dedupe-dev-v1
```

Снапшот для дедупа снимается один раз с копии серверной базы:
`python -m eval.evaluate_dedupe --freeze` с `DB_PATH`, указывающим на копию.
Ошибки последнего прогона сохраняются в `data/eval/errors_<версия>.csv` для разбора.
